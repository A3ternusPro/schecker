# AETERNUS SEO Audit — описание проекта

Файл на случай потери переписки. Приложите его вместе с файлами комплекта — этого достаточно, чтобы продолжить разработку с любого места.

---

## 1. Что это и для кого

Инструмент SEO-специалиста для технического аудита сайтов и подготовки технического задания на доработку.

**Кто пользуется.** SEO-специалист, ведущий клиентские проекты. По итогам аудита отдаёт клиенту ТЗ в Google Docs.

**Что было до.** Аудит по памяти и разрозненным заметкам, ТЗ вручную в Google Docs. Формулировки переписывались заново на каждом проекте и расходились между собой.

**Приоритет — Яндекс.** Это определяет состав и вес проверок: коммерческие факторы важнее ссылочного, Вебмастер и Яндекс Бизнес в приоритете над Search Console, аргументация через ЭПОС, а не только E-E-A-T.

**Инструменты специалиста:** Screaming Frog, Key Collector, Keys.so, xtool, Topvisor, Яндекс Метрика, Яндекс Вебмастер, Google Search Console.

---

## 2. Что инструмент делает

1. **Конфигуратор.** Опрашивает о проекте по семи осям и собирает список проверок именно под этот сайт. Нерелевантное не показывается.
2. **Чек-лист.** 340 проверок со статусами, комментариями, справкой у каждой, фильтрами и поиском.
3. **Генерация ТЗ.** Отмеченное как ошибка превращается в готовый документ с формулировками, аргументацией и списками действий. Выгрузка в Google Docs через буфер обмена.
4. **Генератор robots.txt** с пресетами систем управления сайтом и проверкой на типовые ошибки.
5. **Раздел GEO** — видимость в ответах генеративных сервисов.
5. **Импорт Screaming Frog** — в планах.

**Что сознательно не делается:** свой краулер (браузер не обойдёт сайт из-за ограничений безопасности), автопроверка коммерческих факторов (отличить настоящую страницу гарантий от заглушки на одно предложение автоматика не может, а ложное «ок» хуже отсутствия проверки), интеграции с API вебмастеров (из браузера без сервера не работают), оценка позиций и семантика (для этого есть Topvisor и Key Collector).

**Текстовая оптимизация в аудит не входит** — это отдельная задача.

## 3. Архитектура

Набор файлов в одной папке, открывается двойным кликом по `checker.html`. Работает офлайн, сервер не нужен.

```
checker.html    разметка
app.js          логика приложения
styles.css      оформление, шесть тем
config.js       оси конфигуратора, теги, пресеты профилей
db.js           340 проверок
library.js      20 блоков и 22 страницы с описаниями для ТЗ
templates.js    80 шаблонов задач, словарь, группы, вводные абзацы
robots.js       генератор robots.txt
help-1…7-*.js   справка, 340 записей
overrides.js    правки пользователя, накрывают базу
admin.html      админка: правка текстов и тем
```

**Почему так.** Данные отделены от логики: правка базы или формулировок не требует трогать код. Файлы подключаются классическими тегами `<script>` — это единственный способ, работающий из файловой системы без сервера. Модули не подходят: браузер блокирует их при открытии файла с диска.

**Ключевое ограничение.** Все файлы грузятся в общую область видимости, поэтому глобальные имена не должны пересекаться. Реестр занятых имён ведётся отдельно.

## 4. Принципы, на которых всё держится

### Постоянные слаги

Каждая проверка имеет идентификатор вида `блок.краткое-описание`. Он **присваивается один раз и не меняется никогда** — ни при переформулировке, ни при переносе в другой блок, ни при смене приоритета. Удалённый слаг не переиспользуется.

К слагу привязаны: справка, шаблон ТЗ, описание из библиотеки, данные Screaming Frog и статусы в сохранённых аудитах. Переименование обрывает все связи и ломает прошлые аудиты.

### Пункт не хранит текст ТЗ

Текст собирается на лету из шаблона, комментария и переменных. Иначе правка шаблона не дошла бы до старых проектов.

### Правило выброса

Предложение с незаполненной переменной не попадает в документ целиком. Поэтому один факт — одно предложение. Позволяет заполнять только известное, не получая обрывков вида «обнаружено ссылок».

### Слой переопределений

Правки пользователя живут в отдельном файле и накрывают базу. Обновление любого моего файла их не затрагивает. **Смешивать нельзя:** если править и в базе, и через админку, победит переопределение, и правка в базе будет выглядеть неработающей.

### Осторожность с автоматикой

Ложная находка в ТЗ хуже пропущенной: подрядчик один раз докажет, что задача выдумана, и доверие ко всему документу упадёт. Поэтому длина метатегов не автоматизируется, отсутствие данных не равно «всё в порядке», а у справки есть отдельное поле «когда это не ошибка».

## 5. Структура данных

### Проверка

```js
{slug:'http.redirect-in-links',  // постоянный идентификатор
 p:'crit',                       // crit | high | med | low
 show:{any:[],all:[],not:[]},    // когда показывать; null — всегда
 t:'текст проверки',
 hint:'строка-подсказка',
 group:'robots',                 // объединение задач в ТЗ, необязательно
 tool:'robots',                  // встроенный инструмент, необязательно
 sub:'слаг-родителя'}            // подпункт, не выводится отдельно
```

### Состояние в проекте

```js
{status:'bad',        // ok | bad | na | null
 source:'manual',     // manual | sf
 note:'комментарий',
 vars:{count:'47'},   // значения переменных шаблона
 prev:'bad'}          // статус в прошлом аудите
```

### Файл проекта

```js
{schemaVersion, dbVersion, meta:{domain,client,author,date,note},
 config:{siteType,sales,industry,geo,se,flags,sections},
 items:{}, custom:[], orphans:[], imports:[]}
```

Тема оформления в проекте не хранится — это настройка человека, а не аудита.

### Справка

```js
{why, how:[], tools:[{t,d}], watch:[], falsePos:[], norm, fix, related:[]}
```

Поля `watch` и `falsePos` — то, чего нет в чужих чек-листах. Они не дают наврать в ТЗ.

### Шаблон задачи

```js
{title, task, facts:[], impact:'ключ из ARG', todo:[],
 vars:[{k,label,type,ph}], table:'название'}
```

## 6. Конфигуратор

Семь осей: тип сайта (8 вариантов), модель продаж (B2C/B2B/смешанная), отрасль (26, отдельной группой регулируемые), география, поисковые системы, что есть на сайте (16 флагов), разделы аудита (9). Плюс 11 пресетов быстрого старта.

**Девять разделов аудита** в порядке следования: техническая часть, коммерческие факторы, блоки на страницах, обязательные страницы, аналитика и сервисы, E-E-A-T, юридические требования, локальное SEO, GEO. Названия и порядок задаются только в `config.js` — второго списка нет намеренно, иначе они расходятся.

Из ответов собирается набор тегов, по нему фильтруются блоки и пункты. Есть производные теги: например, магазин плюс B2C добавляет требования по возврату, каталог плюс B2B — опт и реквизиты.

У каждого варианта ответа показан счётчик влияния. Он же служит отладкой: вариант с нулём означает, что под него не написано ни одного пункта.

---

## 7. Как собирается ТЗ

Три уровня, в порядке приоритета:

| Что есть у пункта | Что попадает в документ |
|---|---|
| Шаблон | Заголовок, «Задача», факты с цифрами, «На что влияет», «Что нужно сделать», ссылка на таблицу |
| Описание в библиотеке | Готовое описание блока или страницы |
| Ничего | Краткая задача с комментарием специалиста |

Если два и более пункта одной группы отмечены как ошибка, они собираются в одну задачу с общей аргументацией.

Порядок разделов: технические правки → создание и доработка страниц → блоки и коммерческие элементы → внешние сигналы. Приоритеты в документ не выводятся.

Перед задачами раздела может выводиться вводный абзац (`SECTION_INTRO`). Сейчас он есть у GEO и честно оговаривает, что рекомендации не гарантируют попадания в ответы генеративных сервисов.

Выгрузка: форматированный HTML в буфер для вставки в Google Docs, файл `.md`, полный чек-лист, таблица задач в TSV для Google Таблиц.

## 9. В работе и в планах

1. **Импорт Screaming Frog** — загрузка папки `Bulk Export → Issues → All`, автостатусы, таблицы с русскими заголовками. Схема привязки колонок готова, нужны образцы выгрузок в формате CSV
2. **Документация** — `docs.html` с оглавлением по главам, включая описание админки
3. **Добавление пунктов через админку** — сейчас требует правки `db.js`
4. Расширение базы под отрасли, резерв из таксономии Screaming Frog
5. Режим сравнения аудитов: поле `prev` в схеме заложено, механика не реализована

## 10. Договорённости по работе

- Архитектура обсуждается **до** написания кода
- Ответы короткие и по делу
- Отдаётся весь комплект файлов сразу: приложение проверяет комплектность и без обязательных файлов не запускается
- База знаний ведётся отдельными файлами и обновляется на каждом шаге
- Изменения проверяются автотестами; они уже ловили ошибки, невидимые при чтении кода

## 11. Известные ограничения

- Вставка ТЗ в Google Docs проверена, остальные способы выгрузки — нет
- Мобильная работа не проверялась
- Область GEO меняется быстро: проверять актуальность раз в квартал
- Библиотека покрывает 42 пункта из 340, шаблоны — 80. Остальное выгружается краткой задачей
- Список перерисовывается целиком при изменении: станет заметно при импорте с сотнями находок

## 12. Что нельзя ломать

1. Слаги существующих проверок
2. Уникальность глобальных имён между файлами
3. Совместимость файлов проектов — при изменении схемы нужна миграция
4. Работу из файловой системы — никаких модулей и внешних зависимостей
5. Принцип «данные отдельно от логики»
6. Единственность источника названий разделов: второй список приводит к расхождению
7. Проверку целостности разметки `REQUIRED_NODES` — она ловит ошибки, невидимые в тестах
